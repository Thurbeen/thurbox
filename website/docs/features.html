Features

A customizable interface #

There is no interface compiled into the binary. thurbox boots a kernel, reads a directory, and draws whatever Lua it finds there — so every pane, the session list included, is a file you can move, turn off, delete, rewrite, or install from someone else. You do not have to write any of it yourself: ask the agent you already have running. The full tour is The Interface.

Where each surface lives #

Surface Kind Where it lives

Bundled means it ships with thurbox and is yours to edit, move or delete — the arrangement included. Installable ones sit in plugins.toml on exactly the same terms: the review pane claims its chord by itself, and the info panel wants one layout.lua line.

Sessions #

Heads up: The session list display is not yet perfect and will keep improving — what it can show is heavily dependent on the signals each agent CLI exposes.

Run multiple coding-agent CLIs side-by-side, each in its own multiplexer pane. A session runs one agent (any harness Fleet has a profile for), each with its own default config. Every session is a Fleet Task: Fleet starts it, keeps it running and reports its status. Sessions persist across crashes, restarts, and even multiple concurrent Thurbox instances — the multiplexer keeps them alive in the background. The multiplexer is tmux on POSIX and psmux on native Windows.

  • Create a session with Ctrl+N : Fleet → place → repository → name and branch → agent. The Fleet step is skipped when only one Fleet is listed. The places and agents offered are the chosen Fleet's, and the agent step is skipped when that Fleet offers one harness. See Fleets and places.
  • Rename a session with Ctrl+E from the session list. The name is the Task's thurbox.dev/name label.
  • Each session row shows the agent's live activity when the CLI reports one (via its terminal title), next to a colored status dot
  • Open URLs in terminal output with Ctrl+Click
  • Select text with mouse drag, copy with Ctrl+C , paste with Ctrl+V . With no selection, Ctrl+C sends SIGINT to the active session.
  • Toggle a shell pane alongside the agent session with Ctrl+T
  • Reorder the list by hand: with the session list focused, Shift+J / Shift+K move the selected session (and its nested children) down/up, and Shift+S sorts sessions alphabetically by name within each repo group. Manual order wins — a status change only recolors the dot, never moves a row — and it survives restarts.
  • Attach to a session's terminal outside Thurbox with fleet attach <task>

Agent Definitions #

The agents are Fleet's harness profiles. Thurbox keeps no agent registry: the agent picker offers the harnesses fleet version --json lists, and a session's Task names its harness. See Agents.

Git Worktrees #

A Task's workspace is a list of URLs, and the runtime of its place makes them. The new-session flow gives each repository it ticks one URL, the first where the agent starts:

  • A repository given a worktree with Alt+W: git+file:///path/to/repo?branch=<branch>#<base> for the first, from the base branch picked, and without #<base> for the others, from their own default branch. All are on the one branch the flow names; a branch that exists is checked out
  • A repository ticked as it is, or an existing worktree opened with →: file:///path/to/repo

runtime-mux makes each worktree under its workspace root (~/.local/share/runtime-mux/workspaces unless its config says otherwise), as a worktree of your checkout itself: its branches are your own, and a commit made in the session is in your repository at once (git worktree list shows it). No mapping is needed: the URL is the whole request. A directory that is no git repository, such as the installed interface, is refused a worktree and runs as it is. On a Fleet on another machine, the runtime makes the worktree there, from that machine's branches.

  • Deleting such a Task (fleet delete task) removes its worktree. Work that exists nowhere else, committed or not, is kept under refs/fleet/preserved/ in your repository, and a new Task can restore it by naming that ref in a git+file URL.
  • Ignored files (build output, caches) are not kept: the repository declares them disposable.

Fleets and places #

Two choices decide where a session runs. The Fleet manages the session. The place is where that Fleet's runtime runs the session's process. A place is named <runtime>/<place>, such as mux/wsl-dev, and local is the Fleet's own machine.

thurbox can follow several Fleets. List them in ~/.config/thurbox/settings.toml. With no [fleets] table, thurbox uses one Fleet on this machine. Once the file lists a Fleet, thurbox uses only the listed Fleets. 

[fleets.laptop]
transport = "local"                     # the default

[fleets.box]
transport = { ssh = "me@box" }
program = "/home/me/.local/bin/fleet"   # ssh does not read your login PATH

[fleets.ubuntu]
transport = { wsl = "Ubuntu" }
  • transport says how thurbox runs fleet: "local", { ssh = "<destination>" } or { wsl = "<distro>" }. program names the fleet binary, and config passes fleet --config <path>
  • The session list follows every listed Fleet as one list. A row shows its Fleet, and its place when the place is not local
  • The agent's pane and its companion shell are the streams fleet attach and fleet shell name, over the link to the session's Fleet. thurbox keeps no file of machines of its own
  • A Fleet that cannot be reached keeps its rows, marked unreachable. They clear once the Fleet answers again
  • Each command for a session goes to that session's own Fleet. A new session goes to the Fleet picked in the new-session flow
  • thurbox starts fleet up for a Fleet on this machine when no manager runs. It never starts one on another machine: there, a user systemd unit runs fleet up (the unit). On this machine, the first thurbox runs fleet init; on another machine, run fleet init there once
  • For a Fleet on another machine, the new-session flow browses that machine's folders and branches through its Fleet (fleet runtime browse, fleet runtime branches), and takes a clone URL that the runtime clones there
  • thurbox-cli doctor checks each listed Fleet and says which one cannot be reached

Parent Sessions (Lead / Worker) #

A Task can name a parent with its gateway.fleet.dev/parent label, so a lead session that spawns workers shows them under it.

  • In the session list, children nest under their parent within the same repo group. Ctrl+J / Ctrl+K navigation walks the tree exactly as rendered.
  • The link is informational only — deleting a lead never deletes its workers. A dangling parent renders the child as a top-level session again.

Inter-Session Messages #

fleet send <task> <text> queues a message for a session's agent, and Fleet's Task controller delivers it on its next pass. One agent hands another a payload this way instead of scraping its terminal. The Task's status.inbox records what was queued and delivered, and --answers <id> marks a message as the answer to a question the Task declared.

Global Search #

Press Ctrl+/ to open a non-modal search strip across the top of the interface. A result carries the pane it belongs to, so search grows a scope whenever a pane returns — sessions is the scope that has a pane today.

  • Sessions match on name, agent, worktree branch and repository and on the text on the agent's screen — the half that finds a session by the error in it.
  • Matches highlight live in the pane itself — matching rows accented, the rest dimmed — rather than being reprinted in the strip. Moving the selection previews it in the list; Esc puts back exactly what you were looking at.
  • Metadata matching is subsequence (typing oc52 finds fix-osc52 ); screen text is matched as a substring, because fuzzy matching against a whole terminal screen matches everything. A session whose metadata already matched is not scanned twice.
  • Nobody pays for it while it is closed. Reading every agent's screen every frame would be a permanent cost for a feature in occasional use, so the strip leaves its query where the kernel can see it and the screen text is served only while it is actually asking.

Responsive layout #

The arrangement adapts to the terminal size, and the thresholds are a file you can edit — ui/layout.lua , not a breakpoint compiled into the binary. It ships arranging two panes between three chrome bands:

Terminal size Arrangement
< 80 cols Centre pane only — the session column is dropped
>= 80 cols Session column (25%, min 20 cols) + centre pane
< 20 rows The header band is dropped to keep the panes usable

The centre pane is never dropped — it takes whatever the session column leaves. Everything else is yours: change a percentage, reorder the bands, or delete a line to drop one. The function only arranges , so it never calls a plugin and a mistake in it cannot break one. See the interface for how it is resolved before any plugin draws.

Themes #

Thirty-six built-in palettes (twenty-eight dark, eight light) switch live with Ctrl+Y (or F4 ) and persist across restarts.

OS Notifications #

When a session crosses into a needs-you state — the agent rang the terminal bell or emitted an OSC 9 / OSC 777 notification (usually because it is waiting on an answer or has finished a task) — Thurbox fires an OS desktop notification, so you can react without watching the TUI. The notification body is the agent's last OSC message, or Waiting for input otherwise.

  • Linux dispatches over dbus and supports click-to-focus : clicking the banner switches the TUI to that session on its next tick. macOS shows the banner but ignores clicks (the modern notification API requires a signed app bundle, which Thurbox is not).
  • It fires only while the TUI is open — the terminal parser that watches for the bell does not run headless — and is deduplicated per session, with the session you are currently viewing skipped by default.
  • Tune it in the [notifications] block of settings.toml ( see Configuration ): opt into the timing-only Busy → Waiting edge for agents that never ring a bell, toggle the sound, or change the dedup floor. Turn the whole feature off with [features] notifications = false .

Mouse Navigation #

The whole TUI is clickable (on by default; disable with the mouse feature flag below):

  • Click a row in any pane to select it and focus that pane. A plugin gets the hit for free: it returns the rects it drew, and the kernel matches the click against them.
  • Click a picker row (theme, Fleet, place, agent, branch, …) to select and confirm in one click. Open modals swallow stray clicks, so a misclick never discards typed input.
  • Hover underlines the row under the pointer; the mouse wheel scrolls the focused terminal and steps the selection while a modal is open (with a draggable scrollbar on long lists).
  • Drag selects terminal text ( Ctrl+C copies); Ctrl+Click opens a URL.

Feature Flags #

Behaviour that reaches outside the interface is switched in ~/.config/thurbox/settings.toml under [features] (seeded commented-out, so the defaults apply when absent). Every flag defaults to true — including version_check and auto_update , which reach the network, so they are the two most worth knowing you can turn off.

A pane is not switched off here. Panes are files, so turning one off is space on its row in the Interface tab — a decision recorded in plugin-state.json beside your trust grants. That is strictly more than a flag could do: it works for a plugin you wrote, which no compiled-in flag could ever have known about. 

[features]
shell_pane = true     # Ctrl+T per-session shell
mouse = true          # mouse capture: clicks, wheel, drag-select, hover
notifications = true  # OS desktop alerts when a session needs attention
perf_hud = true       # F12 live counters
version_check = true  # GitHub update check (makes a network call)
auto_update = true    # download+verify+replace the binaries on startup (never across a major)

You don't have to hand-edit the file: press Ctrl+, (or F6 ) to open the Settings panel — a modal that views and edits all of settings.toml (the [features] toggles, the [notifications] knobs, and the scalars). Edits apply on Ctrl+S ( Esc discards); the file is also live-reloaded, so feature flags and notification knobs take effect immediately.

Session Persistence #

Sessions are Fleet Tasks, and Fleet's runtime keeps each one's terminal in a multiplexer window, so a session survives Thurbox quitting, crashing or restarting, and several Thurbox instances show the same sessions.

Action Behavior
Ctrl+Q (Quit) Leaves every session running. The next launch shows them again.
Ctrl+D (Delete) Deletes the Task (fleet delete task). Fleet stops the agent and removes the session's worktree, keeping committed work that exists nowhere else under refs/fleet/preserved/. There is no undo.

Headless CLI #

Every session is a Fleet Task, so fleet drives the same sessions as the TUI, from a script. A change made either way shows up in the other within a tick.

To Run
List sessionsfleet list task
Read onefleet get task <name> (JSON)
Create one fleet apply --create-only -f <task.json>
Type into its agentfleet send <task> <text>
Rename it fleet label task <task> thurbox.dev/name=<name>
Attach to its terminalfleet attach <task>
Follow changesfleet watch --json
Delete itfleet delete task <name>

thurbox-cli keeps what is the interface's own: config, doctor, version, update, plugin, ui, schema, editor, notify and perf. thurbox-cli --help lists them.

Deprecated surfaces

thurbox 2.0 replaced the interface, and six of 1.x's panes did not come with it. This page is where they are documented — what each did, what its chord was, and where it lives now — so nothing you were relying on is simply undocumented. Two of the six have since been rebuilt as panes you install, which is the interface-as-plugins claim being cashed rather than a special case.

No data was dropped. Every record these panes edited is still in the same database at the same schema version. Three of the six were only ever views onto records thurbox-cli can already read and write, so those features are intact and merely have no pane. Of the other three, code review and the info panel are back as installable plugins; only the file viewer has no replacement.

The six, at a glance #

Surface 1.x chord Status Where it is now
Code review Ctrl+X / F7 A plugin thurbox-code-review — and it takes the chord back
File viewer Ctrl+E / F3 No replacement 1.x keeps it. Nothing is withheld — nobody has written the pane.
Info panel Ctrl+B / F2 A plugin thurbox-info-panel — one line in your arrangement
Tasks pane Ctrl+W / F5 Pane only thurbox-cli task
Automations pane Ctrl+P Pane only thurbox-cli automation — and they still fire on their own

Everything else survived the interface change, because only the interface changed: sessions, git worktrees, remote SSH and WSL hosts, agent definitions, extensions, hooks and status reporting, the mailbox queue, themes, notifications, and the whole of thurbox-cli.

Gone from the binary #

These three were rendering, not records, so none of them could move to thurbox-cli. Two are back as panes maintained outside thurbox, each its own repository, each installed by cloning it: 

thurbox-cli plugin install git+https://github.com/Thurbeen/thurbox-code-review
thurbox-cli plugin install git+https://github.com/Thurbeen/thurbox-info-panel

Installing a pane records it in plugins.toml with the commit it resolved to in plugins.lock, so thurbox-cli plugin sync reproduces the same interface on your next machine, and plugin update moves it forward when you ask. What is still owed is tracked in the repository under openspec/changes/v2-parity-gaps/, which is also the honest answer to “when”: written down and prioritised, not scheduled.

Code review

Every session is a git worktree on a branch forked from a base, so “review what this agent built” mapped cleanly onto the session model. Ctrl+X (or F7) opened a native, GitHub-style diff reviewer in the central pane — rendered by thurbox itself, with no external binary and no nested TUI.

  • What to review. The whole branch (<base>..HEAD), a single commit, or the uncommitted working changes — switched with t.
  • Changed-files tree. The file-viewer column listed changes as a folder tree with coloured status glyphs (M/A/D/R) and per-file +/- counts; the diff body was syntax-highlighted, unified or true side-by-side (v).
  • Comments. Line, file, or review-summary comments classified as issue / suggestion / note / praise, composed inline at the line.
  • Mark reviewed & fold. A file or hunk marked reviewed with r/R folded to just its header, tree-style.
  • Feedback loop. y copied the review as markdown; e sent the whole review back into the agent as a prompt to address it. Submitting to GitHub or GitLab was deliberately out of scope.

Comments and reviewed-marks are still in SQLite, keyed per session against the session's write-once base branch — so a review you left in 1.x is still there if you go back to it.

Back as a pane: thurbox-code-review rebuilds all of the above on the plugin kernel and is the first consumer of the diffs the kernel computes on its workers. It needs no change to your arrangement — it takes the centre slot beside the agent and declares itself to the action band, so Ctrl+X / F7 work again the moment it is installed. Two keys are spelled differently on purpose: r is refresh, as it is in every other pane, and marking a file seen is m. It asks for one capability (run) and only for the two review targets the kernel does not compute for itself — the uncommitted working changes and a single commit; untrusted, it still draws the branch diff and the target picker names what it cannot serve rather than hiding it.

File viewer

Ctrl+E / F3 opened a right-hand column with an expandable tree of every worktree and additional directory belonging to the active session — read lazily, one directory at a time, so a large repository cost nothing until you opened into it. It had its own in-file text search on /, which was unrelated to global search and is the one / the interface kept.

Info panel

Ctrl+B / F2 showed the active session's metadata at terminal widths of 120 columns or more: its agent, its repositories and branch, its parent session, the state of its git worktree (Changes:), whether it was behind its base (Sync:), and whether its status hooks were wired or degraded (Hooks:) — alongside host metrics and agent usage.

Back as a pane: thurbox-info-panel draws all of it — the session readouts, the worktree state, host metrics and agent usage — and asks for no capability at all, because every number is already in the snapshot the kernel publishes. It is a column rather than a centre view, so it wants one line in your layout.lua to say where the column goes; its README carries the line, including the max width that stops a panel of labels and values being handed a third of a wide screen.

Still here, just without a pane #

These three were views onto records, and the records did not move. The feature works; you reach it from thurbox-cli instead of from a pane.

Tasks

A todo list whose items connect to a coding agent: send the task into a running session, or spawn a fresh one seeded with it — and an unconnected task is a plain local todo. The pane (Ctrl+W / F5) let you edit in place, cycle status with Space and trigger with r. All of that is thurbox-cli task (alias todo): 

thurbox-cli task create --title "fix the OSC 52 path" --description "$(cat notes.md)"
thurbox-cli task list
thurbox-cli task run <id>          # send or spawn, and advance to in-progress
thurbox-cli task edit <id> --status done

Tracker sync is unaffected by the pane's removal, because it never used the pane: tasks rows carry a source and an external id, and task create --source … --external-id … upserts against them. thurbox ships no provider integration — that is a script you write, or one somebody publishes as an extension.

Automations

Named, scheduled agent runs — one-shot or recurring cron, sending a prompt to a session, spawning a fresh one, or running a shell command headlessly. The pane (Ctrl+P) sat beneath the session list with an in-place editor and run history.

They still fire. Scheduling never lived in the interface: a detached tmux heartbeat keeper runs automation tick every minute whether or not thurbox is open, so an automation authored before the upgrade keeps running afterwards with nothing to do. What you lost is the editor, not the scheduler. 

thurbox-cli automation list
thurbox-cli automation runs <id>   # the run history the pane used to render
thurbox-cli automation run <id>    # fire one now

Their chords are unbound, not reused #

Ctrl+X, Ctrl+E, Ctrl+B, Ctrl+W, Ctrl+P and F2/F3/F5/F7 do nothing rather than something else. That is deliberate and it is asserted by a test: muscle memory that finds nothing is a much smaller problem than muscle memory that finds a different feature. When one of these panes returns — from us or from you — its chord is waiting for it.

Bringing one back yourself #

The reason this list is short prose rather than a roadmap is that panes are files now. A replacement does not have to come from us, and it does not have to be a copy: a plugin declares its own chord, takes a slot, and draws whatever it likes from the session snapshot — and one that runs a program can shell out to git diff or git status in the session's own worktree, on the session's own host. 

thurbox-cli plugin new my-diff   # writes a file that already loads
thurbox-cli plugin check         # loads the interface the way thurbox does

If a missing pane is what keeps you on 1.x, that is a supported place to be — see Using v1 for how to pin it and how to come forward later.

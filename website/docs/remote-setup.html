Run a session on another machine

Thurbox stays on your computer. The agent, repository, and tmux window run on the selected host. Start with a plain Linux SSH host; the other routes only change how OpenSSH reaches it.

  • Plain Linux SSH
  • SSH bastion
  • AWS Systems Manager
  • Google Cloud IAP
  • Azure Bastion
  • WSL

The cloud commands were checked against the linked provider documentation, but were not executed against cloud accounts. Supply your own identity, network access, permissions, and SSH key. Thurbox does not manage cloud credentials or IAM. An isolated container check created, listed, and inspected a remote tmux session with share_sessions = false. Its shared-host CLI check could not run because that container's libc is older than the local binary requires.

Plain Linux SSH

  1. Install Thurbox, thurbox-cli, and OpenSSH on your computer. On the Linux host, run sshd and install Git, tmux 3.2 or newer, your coding agent, and its credentials. Clone the repository on the host. Use its absolute path in Thurbox.
  2. Add a local ~/.ssh/config alias, substituting your hostname and user: 
    Host devbox
    HostName devbox.example.com
    User remote-user
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
    Run ssh devbox 'printf ready'; it should print ready without a password prompt. Verify the host key through your normal SSH process. Then check the remote prerequisites and command path: 
    ssh devbox 'git --version && tmux -V && command -v codex && git -C /srv/project rev-parse --is-inside-work-tree >/dev/null'
    Replace codex and /srv/project with your agent and the host's absolute repository path. If the agent is absent from the remote command PATH, see path_prepend in the host configuration.
  3. Add this to local ~/.config/thurbox/hosts.toml and restart Thurbox: 
    [[hosts]]
name = "devbox"
destination = "devbox"
    The name is what --host takes. By default, share_sessions = true: the host's database records the session, so other Thurbox instances using that host can see it. Thurbox provisions a compatible host CLI when missing. Set it to false if this local instance should own those records. See the full field reference.
  4. Create a session, then inspect it: 
    thurbox-cli session create --name remote-work --host devbox \
  --repo-path /srv/project --agent codex
thurbox-cli session list
    Use your configured agent; --agent shell is useful for a first transport check. In the TUI, press Ctrl+N, choose devbox in the host picker, then choose a remote repository and agent. Remote sessions show a ☁ marker.

The host's tmux window keeps running after a local Thurbox restart. Check with thurbox-cli session list; use thurbox-cli session sync --host devbox to refresh sessions created on the host. For a connection failure, try ssh -v devbox true. If SSH succeeds, check the remote Git, tmux, agent, repository path and credentials. If the host cannot run the provisioned CLI, set share_sessions = false and restart Thurbox; this local instance then owns the session records.

Other OpenSSH routes

Each route changes the SSH alias and hosts.toml destination. It still needs the same Linux host prerequisites. Restart Thurbox after editing hosts.toml; run each SSH check before its Thurbox create command.

SSH bastion

You need SSH access to the jump host and private host, with network access between them. OpenSSH documents ProxyJump. 

Host jump
    HostName jump.example.com
    User jump-user

Host private-dev
    HostName private-dev.internal.example.com
    User remote-user
    ProxyJump jump
[[hosts]]
name = "private-dev"
destination = "private-dev"
ssh private-dev 'printf ready'
thurbox-cli session create --name remote-work --host private-dev --repo-path /srv/project --agent codex
thurbox-cli session list

AWS Systems Manager

The operator must enable an EC2 managed node with running SSH and compatible SSM Agent, Session Manager endpoints and ssm:StartSession permission for AWS-StartSSHSession. Install AWS CLI and its Session Manager plugin locally, authenticate with your organization's AWS profile, and supply an SSH key accepted by the instance. Follow the AWS SSH guide and CLI options. Session Manager command logging is unavailable for SSH sessions: it sees an encrypted tunnel. Replace the instance ID, Linux user, PROFILE_NAME, and REGION below. 

Host aws-dev
    HostName i-EXAMPLE
    User ec2-user
    IdentityFile ~/.ssh/ec2_key
    ProxyCommand sh -c "aws ssm start-session --profile PROFILE_NAME --region REGION --target %h --document-name AWS-StartSSHSession --parameters 'portNumber=%p'"
[[hosts]]
name = "aws-dev"
destination = "aws-dev"
ssh aws-dev 'printf ready'
thurbox-cli session create --name remote-work --host aws-dev --repo-path /srv/project --agent codex
thurbox-cli session list

Proxy syntax: AWS documentation checked; cloud connection not executed here.

Google Cloud IAP

The operator must allow IAP TCP forwarding to SSH, grant IAP and VM login permissions, and configure SSH keys or OS Login. Install and authenticate gcloud locally. Google's OpenSSH instructions first establish the key, then use start-iap-tunnel --listen-on-stdin. Replace the uppercase placeholders. 

gcloud compute ssh VM_NAME --project=PROJECT_ID --zone=ZONE --tunnel-through-iap
Host gcp-dev
    HostName VM_NAME
    User VM_USER
    IdentityFile ~/.ssh/google_compute_engine
    ProxyCommand gcloud compute start-iap-tunnel %h %p --listen-on-stdin --project=PROJECT_ID --zone=ZONE --verbosity=warning
[[hosts]]
name = "gcp-dev"
destination = "gcp-dev"
ssh gcp-dev 'printf ready'
thurbox-cli session create --name remote-work --host gcp-dev --repo-path /srv/project --agent codex
thurbox-cli session list

Commands: Google documentation checked; project connection not executed here.

Azure Bastion

The operator must deploy Bastion Standard or Premium with native client support, grant the required Reader roles, and allow Bastion to reach VM SSH. Install and sign in to Azure CLI with the Bastion extension and select the correct subscription. Microsoft's prerequisites and Linux tunnel steps give the command below. Replace all uppercase placeholders and leave the tunnel running in another terminal while Thurbox uses it. 

az login
az account set --subscription SUBSCRIPTION_ID
az network bastion tunnel --name BASTION_NAME --resource-group RESOURCE_GROUP \
  --target-resource-id VM_RESOURCE_ID --resource-port 22 --port 2222
Host azure-dev
    HostName 127.0.0.1
    Port 2222
    User VM_USER
    IdentityFile ~/.ssh/azure_vm_key
    HostKeyAlias azure-dev-vm
[[hosts]]
name = "azure-dev"
destination = "azure-dev"
ssh azure-dev 'printf ready'
thurbox-cli session create --name remote-work --host azure-dev --repo-path /srv/project --agent codex
thurbox-cli session list

Tunnel syntax: Microsoft documentation checked; subscription connection not executed here. Verify the VM's SSH host key through your normal process.

WSL

On Windows, Thurbox discovers other WSL distros automatically; no SSH server or hosts.toml entry is needed. Install Git, tmux, and your agent inside the distro, with the repository on its Linux filesystem. Press Ctrl+N and select the distro, or use --host DISTRO_NAME. The distro Thurbox itself runs in is local; sibling distros appear as remote options. See host configuration.

These playbooks use the shipped tmux SSH/WSL backend. Optional RMUX and Herdr remote support remains future work.

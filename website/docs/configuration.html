Configuration

Every knob Thurbox reads, where it lives, and how it behaves. One file per audience/lifecycle: hand-edited registries are TOML, the machine-written keybindings are JSON. Thurbox keeps no database: every session is a Fleet Task.

Dev builds (version 0.0.0-dev ) use thurbox-dev in place of thurbox in every path below, plus a thurbox-dev tmux socket, so a development checkout never touches your real setup. All paths respect $XDG_CONFIG_HOME / $XDG_DATA_HOME .

Multiplexer selection

A session's terminal belongs to Fleet's runtime. runtime-mux starts it in this platform's multiplexer: tmux (3.2 or later) on Linux and macOS, psmux (3.3.8 or later) on Windows. Thurbox does not read a top-level multiplexer key in settings.toml, and names one at startup.

Files at a glance #

File Format Edited by Read Purpose
~/.config/thurbox/settings.toml TOML you / Settings panel live (mtime poll) tuning knobs + feature flags
~/.config/thurbox/themes.toml TOML you startup custom theme palettes
~/.config/thurbox/ui/ Lua you live (watched, 120 ms debounce; F10 forces) the interface itself — one file per pane, plus layout.lua and lib/
~/.config/thurbox/ui/plugins.toml TOML you (or thurbox-cli plugin) on each plugin command what the interface is composed of — a source, a destination file and an optional pin, per installed pane
~/.config/thurbox/ui/plugins.lock TOML thurbox-cli plugin on each plugin command what each entry resolved to, and the digest of every file delivered. Machine-written — commit it beside the spec and the same interface reproduces elsewhere
~/.config/thurbox/ui.json JSON F1 / Interface tab (or you) startup your decisions about the interface: rebound chords, plugin settings, the action band's order
~/.config/thurbox/plugin-state.json JSON Interface tab (or thurbox-cli plugin) startup what a plugin may do: files trusted and plugins turned off
~/.config/thurbox/interface.json JSON thurbox startup, and after each change theme, editor command, manual session order, companion shells
~/.local/share/thurbox/thurbox.log text thurbox — logs (incl. config warnings)

settings.toml reloads live : the TUI polls its mtime (~1/s) and applies edits with a confirmation toast — no restart. The shell_pane/perf_hud feature flags apply immediately; the [notifications] knobs, the mouse/notifications/version_check/auto_update feature flags, and the write-once scalars take effect on the next launch and the toast says so. A change to [fleets] or themes.toml needs a restart.

Config problems land in the log file. Unknown TOML keys are tolerated and reported by name, while a syntax or type error falls back to the defaults. Check everything from the command line: 

thurbox-cli config validate   # strict parse of every file; exit 1 on problems
thurbox-cli config show       # effective config + where each value came from

Which file do I edit?

A task-to-file map so you don't have to scan every section to find the right knob. None of these files need to exist on a fresh install — every one is seeded (commented-out where applicable) on first run, and absent files fall back to built-in defaults.

Add a coding agent a harness profile in Fleet (Agents)
Run sessions on another machine a Fleet there, listed in settings.toml's [fleets.<name>]; or a place in Fleet's [runtimes.<name>.places] (Fleets and places; runtimes and their places)

Set the Ctrl+O editor, pick a theme interface.json

Fleets #

Every session is a Task of a Fleet. Thurbox follows each Fleet through its command line: fleet watch for the session list, and fleet apply, send and delete for your actions. The agents a session can run are that Fleet's harness profiles (Agents).

The [fleets.<name>] tables in settings.toml list the Fleets to follow. Each table is one Fleet: on this machine, over ssh, or in a WSL distro. With no [fleets] table, Thurbox follows one Fleet: the fleet on this machine. Once the file lists a Fleet, Thurbox follows only the listed Fleets, so add this machine's Fleet too if you want it. A change takes effect on the next launch. 

[fleets.laptop]
transport = "local"                     # the default
program = "fleet"                       # the default: a name on PATH or a path

[fleets.box]
transport = { ssh = "me@box", ssh_opts = ["-p", "2222"] }
program = "/home/me/.local/bin/fleet"   # ssh does not read your login PATH
config = "/home/me/.config/fleet/config.toml"   # optional: `fleet --config <path>`

[fleets.ubuntu]
transport = { wsl = "Ubuntu" }
Key Default Purpose
transport "local" how Thurbox runs fleet: "local", { ssh = "<destination>", ssh_opts = [...] } or { wsl = "<distro>" }
program "fleet" the fleet program on that machine. ssh runs it with that machine's non-login PATH, so give a full path when fleet is in ~/.local/bin, where the install script puts it
config none Fleet's config file, given as fleet --config <path>. Without it, Fleet reads FLEET_CONFIG, then its per-user file (~/.config/fleet/config.toml)
  • One list. The session list follows every listed Fleet as one list. A session of a Fleet on another machine shows its Fleet, and its place when the place is not local.
  • Unreachable Fleets. When Thurbox cannot reach a Fleet, that Fleet's sessions stay in the list, marked unreachable. Thurbox tries again every 2 seconds.
  • Each command goes to its session's own Fleet. Send, rename and delete go to the Fleet that holds the session. The new-session modal (Ctrl+N) asks for the Fleet first, and skips that step when only one is listed.
  • The manager. For a Fleet on this machine, Thurbox starts fleet up when no manager runs. It never starts one on another machine or in WSL: keep a fleet up running there yourself.
  • Compatibility. Thurbox first asks each Fleet for fleet version --json. A Fleet that does not speak fleet/v1alpha1 shows as incompatible and gets no command.

thurbox-cli doctor checks each listed Fleet: whether Thurbox can reach it, and whether its manager runs.

A Fleet on another machine

Run the Fleet on the machine where the agents should work, here box. The agents keep working when your laptop sleeps.

  1. On box, install fleet, runtime-mux, tmux and a coding agent (Installation), then run fleet init.
  2. On box, install a user systemd unit that runs fleet up. A user service does not read your login PATH: set Environment=PATH to the directories that hold fleet, runtime-mux, tmux and your coding agents. The unit below assumes the install script's ~/.local/bin; adjust both paths for another install location. KillMode=process keeps the tmux server that fleet up starts, and every session on it, when the unit stops or restarts.
  3. On the laptop, add a [fleets.box] table with transport = { ssh = "me@box" } and the full program path.
  4. Run thurbox-cli doctor, then start thurbox.
[Unit]
Description=Fleet manager

[Service]
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
ExecStart=%h/.local/bin/fleet up
KillMode=process
Restart=on-failure
RestartSec=15

[Install]
WantedBy=default.target
loginctl enable-linger "$USER"
systemctl --user enable --now fleet.service

Each ssh call uses BatchMode and a shared connection, so authentication comes from your ~/.ssh/config and agent; Thurbox never handles credentials. In the new-session modal you browse box's folders, starting at box's home (~ is that home), pick a remembered repository, or paste a clone URL, which the runtime clones there. Alt+W gives a repository a worktree there: its base branch comes from box's branches, and the runtime makes the worktree on box.

A Fleet in WSL

On Windows, a Fleet can run inside a WSL distro. Install fleet, runtime-mux, tmux and a coding agent in the distro, run fleet init there. Keep fleet up running with the same user systemd unit as a Fleet on another machine, installed inside the distro (systemd must be on: [boot] systemd=true in /etc/wsl.conf). Then add the distro on the Windows side: 

[fleets.ubuntu]
transport = { wsl = "Ubuntu" }

settings.toml #

Scalar tuning knobs plus the [features] switches, seeded fully commented-out (defaults apply when absent). Only knobs a user plausibly wants are exposed; internals stay hardcoded. The file is live-reloaded via mtime poll: the UI-panel feature flags apply immediately, while the [notifications] knobs, the mouse/notifications/version_check/auto_update feature flags, and the write-once scalars take effect on the next launch.

Settings panel. You don't have to hand-edit the file: the TUI has a Settings modal opened with Ctrl+, (or F6 ) that views and edits all of settings.toml — the [features] toggles, [notifications] knobs, and scalars. It edits a working copy and applies only on Ctrl+S (Esc discards); the panel writes back through the same file, preserving its documentation comments.

Key Default Purpose
scrollback_lines 1000 terminal scrollback kept per session
hidden_terminal_secs 30 seconds a session can be off screen before its terminal grid is dropped (rebuilt from tmux when shown); 0 keeps every grid
two_panel_min_cols 80 width below which only the terminal renders
git_poll_secs 5 seconds between git stats of a session (the diffstat beside it); 0 turns the polling off

A complete settings.toml showing every knob at its default — copy this and uncomment what you want to change (the UI-panel feature flags apply live; the [notifications] knobs, the mouse/notifications/version_check/auto_update flags, and the write-once scalars take effect on the next launch): 

config_version = 1

# Scalar tuning knobs (top level)
scrollback_lines      = 1000   # terminal scrollback kept per session
hidden_terminal_secs  = 30     # seconds off screen before a grid is dropped; 0 = keep all
two_panel_min_cols    = 80     # width below which only the terminal renders
git_poll_secs         = 5      # seconds between git stats of a session; 0 = off

[features]
shell_pane    = true
perf_hud      = true
mouse         = true
notifications = true
version_check = true           # makes a network call
auto_update   = true           # downloads + replaces binaries

[notifications]
backend             = "auto"   # auto / dbus / windows / off
suppress_for_active = true     # skip the session you're currently viewing
sound               = true     # play the OS default notification sound
min_interval_secs   = 5        # per-session floor between notifications

[features] — whole-feature switches

Switch off behaviour that reaches outside the interface. All default to true — version_check and auto_update included, which both reach the network. shell_pane and perf_hud apply live on save; mouse, notifications, version_check and auto_update, and the write-once scalars, wait for the next launch. Data is never touched, so re-enabling a flag is lossless.

A pane is not switched off here. Panes are files, so turning one off is space on its row in the Interface tab (Ctrl+, then ]), recorded in plugin-state.json.

Key Default Controls
shell_pane true per-session shell toggle (Ctrl+T)
perf_hud true the performance HUD (F12)
mouse true mouse capture: clicks, wheel, drag-select, hover, scrollbars
notifications true OS desktop notifications when a session needs attention
version_check true GitHub update check: TUI header “update available” badge + thurbox-cli version --check
auto_update true silent self-update: download + verify + replace the binaries on startup + thurbox-cli update

mouse = false skips terminal mouse capture entirely, so the terminal keeps its native mouse behavior. notifications = false keeps the background dispatcher thread from ever starting (zero overhead) and silently no-ops every transition; the session status display itself is unaffected.

version_check = true enables the update check. On launch the TUI reads a cached result (~/.local/share/thurbox/version-check.json) and, if it is older than 24 h, fires a single best-effort background fetch of GitHub's latest release (via curl/wget); a newer release shows a ↑ vX.Y.Z available badge next to the version in the header. The fetch never blocks startup and failures are silent. Dev builds (0.0.0-dev) never show the badge. The same flag enables thurbox-cli version --check (thurbox-cli version with no flag always prints the current version).

auto_update = true goes a step further than version_check: instead of just showing a badge, the TUI silently updates itself on startup. After the same 24 h cache check, if a newer release exists it downloads that release's tarball + checksums from GitHub Releases (curl/wget), verifies the SHA256 (sha256sum/shasum), extracts it (tar), and atomically replaces the installed thurbox/thurbox-cli binaries in place — mirroring scripts/install.sh. The download is verified before any installed file is touched, so a failed download leaves the current binaries untouched; the step runs before the TUI takes the terminal and is best-effort. The replaced binary takes effect on the next launch, so the TUI shows an “Updated to vX.Y.Z — restart to apply” status line. thurbox-cli update performs the same update on demand (--force bypasses the up-to-date and dev-build guards, never the major line); dev builds (0.0.0-dev) never auto-update. version_check and auto_update are independent — enable either or both.

Auto-update never crosses a major version. A 2.x install only ever takes 2.x releases. A new major is reported by thurbox-cli version --check and thurbox-cli update — and never installed, because a silent crossing could hand you a different program under the same binary name. No flag crosses, --force included: moving to a new major is a reinstall.

[notifications] — OS notification settings

Surfaces an OS notification when a session crosses into a state that needs the user's attention (the agent rang the terminal bell or emitted an OSC 9 / OSC 777 message — usually because it's waiting on an answer or has finished a task). Linux dispatches via dbus and supports click-to-focus: clicking the banner writes a focus request that the running TUI reads on its next tick and switches to that session. macOS shows the banner but ignores clicks (the modern UNUserNotificationCenter API requires a signed app bundle, which thurbox is not). The notification body is the agent's last OSC message when present, otherwise Waiting for input. Only fires while the TUI is open — the agent terminal parser is what sees the bell, and it doesn't run when thurbox isn't. Gated by the notifications feature flag above.

Key Default Purpose
backend auto delivery backend (auto / dbus / windows / off): auto picks dbus on a Linux desktop, the WSL Windows-toast fallback, or the macOS native banner; off drops every notification (a soft switch distinct from the feature flag)
suppress_for_active true skip the notification for the session you're currently viewing
sound true play the OS default notification sound
min_interval_secs 5 per-session floor between two notifications (dedup)

The default-on Attention trigger is the right knob for any agent that respects the terminal bell / OSC 9 / OSC 777 conventions (Claude Code out of the box, for example).

themes.toml #

User-defined themes, offered in the Ctrl+Y picker alongside the thirty-six built-in presets and persisted by name like any preset. Each [[themes]] entry starts from a built-in base and overrides only the colours it names: 

[[themes]]
name = "my-mocha"            # stable id; must not shadow a built-in
display_name = "My Mocha"    # picker label (default: name)
base = "catppuccin-mocha"    # starting palette (default: default)
accent = "#fab387"
app_bg = "reset"             # keep the terminal's native background

Colours accept anything ratatui parses: #rrggbb , ANSI names ( red , lightcyan ), indexed ( 14 ), or reset . Bad colours and built-in name collisions degrade to startup warnings.

Rebound chords (ui.json) #

Rebindings live in ~/.config/thurbox/ui.json. The panes you have turned off and the files you trust live beside it, in plugin-state.json. Its bindings object maps an action id to the one chord string that action answers to. Action ids are dotted and lowercase — the kernel's own are help.open , settings.open , themes.open and palette.open , and panes declare theirs in the same style ( sessions.delete , sessions.rename , …): 

{ "bindings": { "themes.open": "f2", "sessions.delete": "f3" } }
  • The editing path is the F1 panel : select an action, press the chord. It takes effect on the next keystroke and persists itself.
  • Chord syntax: [ctrl+][alt+][shift+][cmd+]<key> where <key> is a letter, f1 – f12 , or a named key ( enter , esc , tab , arrows, home , end , pageup , pagedown , backspace , delete , insert ). Case-insensitive. cmd (aliases super , command , win ) is the macOS Command key, delivered only by kitty-keyboard-protocol terminals.
  • Binding a chord another action already claims in the same context takes it: your override is the one that fires. An entry naming an action no plugin declares is dropped silently — a typo just does nothing, which is why the F1 editor, which refuses an unknown action outright, is the safer path.
  • Five chords are reserved and cannot be rebound at all — ctrl+q (quit), f10 (reload), ctrl+h / ctrl+l (focus) and f12 (perf HUD). They are the way out of a pane that consumes every key, so quit is not a declared action and has no id to bind.

See the Keybindings page for the full default chord table.

interface.json #

~/.config/thurbox/interface.json is what the interface remembers between runs: the theme last chosen (the Ctrl+Y picker), the editor Ctrl+O opens (thurbox-cli editor set "<cmd>"), the manual session order and each session's companion shell. thurbox rewrites it whole under a lock every process takes. A missing or unreadable file means the defaults.

Environment variables #

Traces and metrics use the standard OTEL_* variables, the same for Thurbox, Fleet and the runtimes: see Observability.

Variable Used for
XDG_CONFIG_HOME, XDG_DATA_HOME config/data roots
VISUAL, then EDITOR Ctrl+O editor when editor_command is unset
SHELL the Ctrl+T companion shell pane (fallback /bin/sh)
RUST_LOG log filter for thurbox.log
THURBOX_CONFIG_DIR / THURBOX_DATA_DIR relocate this instance's config / data (see below)
THURBOX_SOCKET name the multiplexer socket outright, overriding both

Relocating an instance. THURBOX_CONFIG_DIR and THURBOX_DATA_DIR move thurbox's config and its data, and an instance whose data dir has moved also gets a multiplexer socket of its own , so it cannot create windows on the server holding your everyday sessions. A default instance keeps the socket it has always used — nothing changes for a thurbox you have not relocated. Ask a build which server it is on rather than assuming: thurbox-cli version --json reports it as tmux_socket . The full rules are in the repository's docs/thurbox/config.md (“Relocating an instance”).

Editor resolution order: interface.json’s editor_command → $VISUAL → $EDITOR → error toast.

Versioning #

The TOML files carry a config_version = 1 marker so a future format change can migrate them; current files are version 1 and the field is optional.

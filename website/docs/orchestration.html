Orchestration

Running agents across many repos raises a question that one repo never does: where does the plan live? In Thurbox the answer is Fleet, the engine that manages every session. This page shows how Fleet runs a Task, how to browse it from Thurbox, and how to drive sessions yourself.

Fleet: one session per Task #

Fleet lives in Thurbox's repository (crates/fleet-*), and its reference is on this site. A Task is one unit of work. It names a harness (the agent), a place, a workspace and a brief. Fleet runs one session for it, sends the brief once, records the result the worker reports, and releases the session when you delete the Task.

  • Resources, not chat. Tasks, the ChangeRequests they declare, and the configuration they run with are stored as versioned resources, so the plan outlives every session.
  • Isolated workers. Each Task works in a workspace of its own, which its runtime makes.
  • A reconcile loop. fleet up keeps every Task moving until you stop it. It creates no Task of its own.
  • Forge follow-through. A ChangeRequest mirrors one pull or merge request on GitHub, GitLab, Azure DevOps or Bitbucket.

Install

Thurbox's install script installs fleet and runtime-mux with Thurbox. A source build also builds them. 

curl -fsSL https://raw.githubusercontent.com/Thurbeen/thurbox/main/scripts/install.sh | sh
fleet init     # writes Fleet's config
systemctl --user start fleet.service
thurbox

Thurbox never starts fleet up. Each Fleet needs a user systemd unit that runs fleet up; see Keep fleet up running. To run Fleet alone, see Fleet alone.

Fleet Lens, in Thurbox

Fleet Lens is the Thurbox pane for Fleet: a read-only float that lists every resource kind Fleet serves, Tasks first, with the ones that need a person on top. Alt+K opens it, Enter reads a resource as YAML, and Tab steps through the kinds. It reads Fleet only through fleet … --json and writes nothing. 

thurbox-cli plugin install git+https://github.com/Thurbeen/thurbox-fleetlens
thurbox-cli plugin check

Then trust it, because it runs fleet : Settings ( Ctrl+, ), then ] , select thurbox-fleetlens/plugins/88_fleet_lens.lua and press t . Its README lists its keys, columns and settings.

How Fleet runs a Task # 

fleet apply ─▶ spawn session ─▶ send brief ─▶ worker runs
                                                  │ fleet result
fleet delete ─▶ release session ◀── Concluded ◀───┘

Every Task shows up in the Thurbox session list within a tick, because the interface follows fleet watch. A Task that names a parent with its gateway.fleet.dev/parent label nests under that parent, so a lead's workers sit under the lead. Deleting a lead deletes none of its workers.

Command What it does
fleet apply -f task.json Creates or updates a Task; --create-only refuses a name that is taken, and dispatch: true lets it start
fleet list task · fleet status task <name> --json Every Task; one Task's status and conditions: Spawned, Briefed, Concluded
fleet send <name> <text> Types into the session's agent
fleet result <name> --generation N --outcome … The worker's own report; only that concludes a Task
fleet watch --json Follows every change, one event per line
fleet delete task <name> Releases the session, then removes the Task

Stopping fleet up keeps the sessions, so a restarted manager reconnects to them. Fleet passes no credentials to a session: they stay with the agent.

Start by just asking #

You do not have to write the orchestration yourself. A session's agent can run Fleet's command line like any other command, so from inside any session you can ask for a fleet in English.

  • Using Fleet, start a session per crate of this repository, and send each one a prompt to refactor its crate. Then list the Tasks.

The commands the agent reaches for are fleet apply --create-only, fleet send and fleet list task. To schedule work, apply a CronTask: it creates a Task at each time of its schedule. To prompt one long-lived session on a timer instead, run fleet send from a cron job or a systemd timer. The recipes page has the same thing written as bash, if you would rather commit a script.

Read the state, do not infer it #

A session's state is Fleet's status.sessionState, which the agent's own hooks report through fleet signal. Wait for a state with a bound on the wait, and read the Task again when the wait ends: a timeout is not evidence that the agent finished. A worker's outcome is its status.result, written by fleet result, never the state of its terminal.

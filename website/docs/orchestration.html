Orchestration

Running agents across many repos raises a question that one repo never does: where does the plan live? One ready-made answer is Fleet , an orchestrator that runs its agent sessions in Thurbox. This page starts there, then walks through the Thurbox primitives it is built from, for when you want to drive them yourself.

Fleet: one session per Task #

Fleet is a standalone program, not a Thurbox extension. A Task is a resource that names a harness (the agent), a host, a workspace and a brief. Fleet starts one Thurbox session for it, sends the brief once, records the result the worker reports, and releases the session when you delete the Task.

  • Resources, not chat. Tasks, the ChangeRequests they declare, and the configuration they run with are stored as versioned resources on disk, so the plan outlives every session.
  • Isolated workers. A Task's workspace is a list of URLs its runtime makes: a git URL becomes a worktree of its own, and a file:// URL is a directory used as it is.
  • A reconcile loop. fleet up keeps every Task moving until you stop it. It creates no Task of its own.
  • Forge follow-through. A ChangeRequest mirrors one pull or merge request on GitHub, GitLab, Azure DevOps or Bitbucket.

Install

Fleet ships one binary for Linux, x86_64 and aarch64; it has no Windows or macOS release. To run real sessions it needs Thurbox with thurbox-cli on PATH , and an agent CLI that is installed and logged in. 

curl -fsSL https://github.com/Thurbeen/fleet/releases/latest/download/install-release.sh | sh
fleet init     # the config, offline
fleet up       # the manager; keep it running in its own terminal

Fleet's README covers setup, updates and uninstalling, and its initialization guide covers the config and fleet up .

Fleet Lens, in Thurbox

Fleet Lens is the Thurbox pane for Fleet: a read-only float that lists every resource kind Fleet serves, Tasks first, with the ones that need a person on top. Alt+K opens it, Enter reads a resource as YAML, and Tab steps through the kinds. It reads Fleet only through fleet … --json and writes nothing. 

thurbox-cli plugin install git+https://github.com/Thurbeen/thurbox-fleetlens
thurbox-cli plugin check

It needs Thurbox 2.76.2 or later. Then trust it, because it runs fleet : Settings ( Ctrl+, ), then ] , select thurbox-fleetlens/plugins/88_fleet_lens.lua and press t . Its README lists its keys, columns and settings.

How Fleet runs a Task # 

fleet apply ─▶ spawn session ─▶ send brief ─▶ worker runs
                                                  │ fleet result
fleet delete ─▶ release session ◀── Concluded ◀───┘

While fleet up runs, you drive Tasks with the CLI:

Command What it does
fleet apply -f task.json Creates or updates a Task; dispatch: true lets it start
fleet list task · fleet status task <name> Every Task and its phase; one Task's conditions: Spawned, Briefed, Concluded
fleet send <name> <text> Messages the running session
fleet result <name> --generation N --outcome … The worker's own report; only that concludes a Task
fleet delete task <name> Releases the session, then removes the Task

fleet up holds one manager lease and sweeps once a second by default. Ctrl-C releases the lease and keeps the sessions, so a restarted fleet up reconnects to them. Fleet passes no credentials to a session: they stay with the agent and its host.

Start by just asking #

You do not have to write the orchestration yourself. Every session is a Fleet Task, and a session's agent can run Fleet's command line like any other command, so from inside any session you can ask for a fleet in English.

  • Using Fleet, start a session per crate of this repository, and send each one a prompt to refactor its crate. Then list the Tasks.
  • Create a nightly automation that sends “triage new issues” to the triage session on weekdays at 09:00.

The commands the agent reaches for are fleet apply --create-only, fleet send, fleet list task and thurbox-cli automation create. Everything it does shows up in your running TUI within a tick, because the TUI follows fleet watch. The recipes page has the same thing written as bash, if you would rather commit a script.

Read the state, do not infer it #

A session's state is Fleet's status.sessionState, which the agent's own hooks report through fleet signal. Wait for a state with a bound on the wait, and read the Task again when the wait ends: a timeout is not evidence that the agent finished. A worker's outcome is its status.result, never the state of its terminal.

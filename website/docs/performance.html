Multiplexer performance

This four-configuration comparison ran on one four-core NixOS machine: standalone tmux, standalone Herdr, standalone RMUX, and Thurbox using tmux. Each host used isolated state, the same session command, and five measured repetitions after one warm-up. Thurbox using RMUX remains unmeasured while its implementation is validated. Debian timing was unavailable under concurrent process churn; local timing remains pending amid other work. Read the full report.

Each configuration hosted an actual Codex TUI using a loopback Responses fixture. These numbers include Codex CPU and memory but exclude the shared mock server. Each host kept the checked burst tail, showed no stale first view, and lost no typed input. The 65-second idle window at 20 sessions recorded 9.15% CPU (p95 9.35%) for Herdr and 0% in the sampled host process set for the other three. A short-lived automation process can escape that process accounting; see the method and caveats.

What the trade-offs mean #

Plain tmux had the smallest measured host memory and quickest idle stand-in echo. RMUX was close to tmux for creation and attach, used more memory, and had a longer tail when another session was busy (11.1 ms p95). Herdr displayed the attached burst soonest and had the quickest busy echo, while its 50-session attached idle CPU reached 121% of one core at p95. Thurbox restarted all three recorded stand-in commands after a clean shutdown; its attached CPU, memory, burst display, and Codex echo were costlier in this run. Choose according to which of these measured behaviors matters for your sessions.

Machine and limits #

These results came from NixOS 26.05 on a four-core Intel Core i5-6500T with 15.5 GiB RAM, tmux 3.6a, Herdr 0.9.1, RMUX 0.10.0, and Codex CLI 0.157.1. Thurbox was built from source commit 1f9bd654. The host order rotated across repetitions, and each used a fresh home, config, socket, and server. The Codex TUI had a local inference fixture and real observed hook status changes; its results include Codex and are not host-only.

A four-core Debian machine passed the quick scenarios and a one-repetition Codex hook probe, but fair full timing was unavailable: CPU pressure stayed around 15–21% with repeated rapid process starts even after benchmark-owned processes were removed. Local timing was also held while other Rust builds ran. Neither host supplied performance cells here. A different CPU, terminal, agent, or provider can change the result; the method records exact commands and tool hashes.

Inspect your interface with F12 #

  1. Open Thurbox and press F12. A perf overlay and a ranked panes table appear. Press F12 again to close them. The HUD is on by default; if the key does nothing, set perf_hud = true under [features] in settings.toml in your Thurbox config directory. This setting applies when you save it.
  2. Leave the interface alone for several seconds. frames counts painted screens; skipped counts loop passes that avoided a paint. A slowly rising frame count and rising skips are normal at rest. renders counts pane render calls, and reused r/g shows reused pane trees and published groups. The frame, republ, and tick rows show median and maximum time for drawing, rebuilding shared data, and loop work. slow names a recent slow operation or pane.
  3. Read the panes table, ranked by total time. p95 is the 95th-percentile render time: 95 of 100 renders finish at or below it. share is the pane's portion of measured frame time, and rend/reuse separates renders from cache reuse. The costliest row is red; a ! marks a diagnostic hint. If a pane's render count keeps climbing while you are idle, read that hint and check whether the pane has a clock, animation, or changing data that calls for those renders.
  4. While the HUD is open, run thurbox-cli perf --plugins in another terminal for every loaded pane, longer names, handler and render times, cache reuse, and the hints in full. The TUI publishes a snapshot every few seconds while timing is active; the CLI reads the latest snapshot. Use --json for a script.

These counters diagnose your own interface. They are not the multiplexer benchmark above, and a busy pane can be doing useful work.

Why the cost changes #

When its interface is closed, Thurbox leaves the sessions in tmux. When it is open, it also paints an editable Lua interface, so CPU and memory rise. It avoids painting unchanged frames and releases the terminal grid of a session that has been off screen. The technical performance report explains those decisions, the F12 counters, and the tests behind them.

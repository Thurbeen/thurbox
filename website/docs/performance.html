Performance at 50 sessions

Same-machine measurements of what it costs to start, keep, and show agent sessions. Read the benchmark report.

  • After closing the interface: 50 idle Thurbox sessions used 0% host CPU and about 9 MiB of measured host memory; Herdr used 22.5% and about 41 MiB.
  • Creating: 50 sessions took 1.81 s in Thurbox, 2.66 s in Herdr, and 0.45 s in plain tmux.
  • Typing: Herdr echoed sooner: 2.23 versus 4.13 ms at rest, and 0.45 versus 1.90 ms with another session busy.

Each cell is a median; lower is better for time, CPU, and memory. The 50-session resource cells show CPU as a share of one core, then PSS memory in MiB. CPU is the host's processing time in a fixed window (100% means one core was busy). PSS counts each host process's fair share of shared memory, so a library used by two processes is counted only once. Both exclude the identical stand-in agents. “Printing” means every agent wrote 10 lines per second; with the UI open, the client displayed one session.

The resource rows combine a Thurbox-only rerun on source 78ca3f93 (25 September) with Herdr and tmux from the earlier three-host run (23 September, Thurbox build 1a6b60c0). They used the same machine but were not interleaved with each other. The typing and burst rows come from a separate three-host final-source run (25 September).

Attached idle Thurbox memory measured 46.9 MiB at the final-head median and 56.7 MiB at p95 (the worst of five repetitions): a short spike after attach remains. The earlier full run before the echo change read 46.0 MiB, and its after run read 52.3 MiB. Those earlier values are not final-head results.

Thurbox still loses to Herdr on typing: 4.13 versus 2.23 ms at rest, and 1.90 versus 0.45 ms with another session busy. In the final-source burst run, the last of 50,000 lines appeared at 269 ms in Thurbox and 158 ms in Herdr. In the same raw run, that attached burst also spent 0.38 s of host CPU and left 37.1 MiB PSS in Thurbox, versus 0.19 s and 23.2 MiB in Herdr. The steady 50-session resource result does not describe every output shape.

Which to choose #

Pick plain tmux when the smallest host cost and quickest local echo matter most. Pick Herdr when typing latency or fast burst display matters most. Thurbox fits when you want its session workflow, low unattended CPU cost, and diagnostics for your own interface panes. The resource advantage at 50 sessions does not hold at every size: with one attached idle session in the earlier full run, Herdr used 1.10% CPU and 22.6 MiB PSS, versus Thurbox's 2.89% and 28.2 MiB.

Inspect your interface with F12 #

  1. Open Thurbox and press F12. A perf overlay and a ranked panes table appear. Press F12 again to close them. The HUD is on by default; if the key does nothing, set perf_hud = true under [features] in settings.toml in your Thurbox config directory. This setting applies when you save it.
  2. Leave the interface alone for several seconds. frames counts painted screens; skipped counts loop passes that avoided a paint. A slowly rising frame count and rising skips are normal at rest. renders counts pane render calls, and reused r/g shows reused pane trees and published groups. The frame, republ, and tick rows show median and maximum time for drawing, rebuilding shared data, and loop work. slow names a recent slow operation or pane.
  3. Read the panes table, ranked by total time. p95 is the 95th-percentile render time: 95 of 100 renders finish at or below it. share is the pane's portion of measured frame time, and rend/reuse separates renders from cache reuse. The costliest row is red; a ! marks a diagnostic hint. If a pane's render count keeps climbing while you are idle, read that hint and check whether the pane has a clock, animation, or changing data that calls for those renders.
  4. While the HUD is open, run thurbox-cli perf --plugins in another terminal for every loaded pane, longer names, handler and render times, cache reuse, and the hints in full. The TUI publishes a snapshot every few seconds while timing is active; the CLI reads the latest snapshot. Use --json for a script.

These counters diagnose your own interface. They are not the multiplexer benchmark above, and a busy pane can be doing useful work.

How to read the results #

These rows come from different builds on the same machine:

  • 23 September 2026, Thurbox 1a6b60c0: creation, plus the Herdr/tmux resource comparators and the one-session example. Summary and raw CSV.
  • 25 September 2026, Thurbox 78ca3f93: resource-only rerun (--hosts thurbox --scenarios resources). Summary and raw CSV.
  • 25 September 2026, Thurbox 78ca3f93: three-host typing and burst rerun. Summary and raw CSV.

The comparison used a four-core Intel Core i5-6500T (2.5 GHz), 15.5 GiB RAM, NixOS 26.05, tmux 3.7c, and Herdr 0.9.1, the latest stable release checked on 25 September 2026. Thurbox was built in release mode from the commits named in the report. The same Python stand-in agent ran on every host. Each scenario used five measured repetitions after one discarded warm-up; latency sent 100 keys per repetition. In the raw summaries, p95 means the 95th percentile: the worst of five scenario repetitions, or the 95th-percentile key among 500 latency samples. Hosts were interleaved within each three-host run; the final resource rerun included only Thurbox. Herdr's documented creation path uses a shell and two CLI calls per session, which affects its creation result.

A real coding agent, a different terminal, remote SSH, macOS, or Windows can change the result. The terminal emulator's own cost was outside the harness. The full benchmark report and the linked raw data include the commands, per-run samples, defaults, and threats to validity. The report also records the different headless grid sizes and the limits of a terminal harness.

Why the cost changes #

When its interface is closed, Thurbox leaves the sessions in tmux. When it is open, it also paints an editable Lua interface, so CPU and memory rise. It avoids painting unchanged frames and releases the terminal grid of a session that has been off screen. The technical performance report explains those decisions, the F12 counters, and the tests behind them.

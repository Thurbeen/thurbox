Why thurbox and Fleet

A control plane for your coding agents

Most agent tools put your sessions side by side on one screen. Fleet goes further: it runs each agent on the machine you name, keeps it to what you declared, lets agents hand work to each other and follows their pull requests. thurbox is the screen on top.

01 · Places

Start a session on any machine

A Task names the place it runs. Fleet's runtime, runtime-mux, reaches this machine, a server over ssh and a WSL distro today.

  1. 1Name a place

    A Task's host is a place, <runtime>/<place>: local, a server you reach over ssh, or a WSL distro. Each place is a few lines of Fleet's config.

    Put the agent where the code, the GPU or the credentials are.

  2. 2Fleet starts it there

    runtime-mux clones the workspace on that machine and starts the agent in tmux there. thurbox lists the session with its place, and its shell opens on the same machine.

    No ssh-ing in to set up a checkout by hand.

  3. 3Quit, and they keep running

    Fleet runs the sessions, not thurbox. Quit thurbox and every agent keeps working. thurbox can also follow other Fleets over ssh or WSL, each in the same list.

    Close the laptop lid: the work on the server goes on.

02 · Declarative

Declare it once, Fleet keeps it true

Fleet works like Kubernetes. You write the state you want as a resource; controllers compare it with what runs and close the gap, sweep after sweep. Nobody has to watch it.

  1. 1Declare

    You write what you want as a resource. A Task names the agent, the place and the brief; fleet apply, thurbox, a script or another agent puts it in the store. TaskConfig, EnvProvider, ChangeRequest and CronTask are resources too.

    One file describes the work, so a script or a schedule can start it too.

  2. 2Compare

    Controllers, run by fleet up, read each spec and observe the runtime. A Task that should run and has no session is a gap to close.

    No babysitting: every sweep finds the Task that should run and does not.

  3. 3Act

    They close the gap through the runtime: make the workspace, start the session, type the brief. The manager records each effect's intent before it runs it.

    After a crash, Fleet looks a spawn up by its key first, so no session starts twice.

  4. 4Write back, sweep again

    They write the phase and the session's state back to the status, then sweep again. After a reboot, they revive the session with the same id and worktree, and the agent's conversation resumes.

    The status stays true, and a reboot costs the agent nothing.

03 · Orchestration

Agents that work together

An agent can run fleet like any other command. A lead splits its work into child Tasks, and Fleet routes what each child says back to the lead. Your team's Slack or Discord is one more way in.

  1. 1Ask in a thread

    Mention Fleet's bot in a Slack or Discord thread. The gateway admits the people your config lists and starts a lead Task tied to that thread. The gateway only moves messages: it never runs a model.

    Start work where your team already talks.

  2. 2The lead splits the work

    The lead's agent runs fleet apply to start child Tasks that name it as their parent. thurbox nests each child under its lead.

    One agent plans; several agents build, each in its own workspace.

  3. 3Children report to the lead

    A child's Questions, Drafts and result reach the lead's inbox, not the thread. The lead answers a Question with fleet send --answers.

    You hear from the lead, not from every worker.

  4. 4News reaches everyone

    The lead's Comments and Questions are posted in the thread. Tasks publish events to a Board, and Fleet adds its own; a Task that subscribes gets a notice in its inbox.

    Agents share what changed without a person passing it on.

04 · Change requests

Pull requests followed for you

Once an agent opens a pull request or merge request, Fleet keeps it up to date with what happens there, on GitHub, GitLab, Bitbucket Cloud and Azure DevOps.

  1. 1The agent opens a change

    The agent pushes, opens a draft with the forge's CLI and runs fleet declare <task> --change-request <url>. Fleet's standing policy tells every agent to do this.

    One line ties the pull request to the Task.

  2. 2Fleet follows it

    Every sweep, controllers read the change on GitHub, GitLab, Bitbucket Cloud or Azure DevOps: its state, checks, reviews, comments, open threads and mergeability.

    Nobody keeps the pull request open in a browser tab.

  3. 3News reaches the agent

    What is new since the last sweep, a review comment, a failed check, a merge, becomes one inbox entry for the agent's session. The agent's own replies are not relayed back to it.

    The agent answers the review and fixes CI without you pasting anything.

05 · Extensible

Extend every layer

Fleet grows the way Kubernetes does: new kinds and the controllers that reconcile them. Each other layer has its own way in too.

  • Fleet plugins

    Your own resource kinds

    A plugin adds a resource kind and the controller that reconciles it, the way a CRD and an operator extend Kubernetes. It is one program in any language that reads JSON and writes JSON; the manager does every write.

    Write a plugin →

  • Harness profiles

    Any agent CLI

    Fleet ships nine harness profiles, among them claude, codex and opencode. A TOML file in Fleet's config adds another agent or replaces a bundled profile.

    Agents →

  • Runtimes

    Your own runtime

    A runtime is any program that speaks the runtime protocol. runtime-mux ships with Fleet; fleet runtime check tests your own against the protocol.

    The runtime protocol →

  • thurbox panes

    An interface you script

    Every pane of thurbox is a Lua file. Move it, turn it off, replace it, or install another from the plugin catalog.

    Plugins →

The interface

thurbox

thurbox is a terminal interface on top of one or more Fleets. It shows every session of every Fleet in one list, with the agent's live terminal beside it. Every pane is a Lua file you can move, turn off or replace.

Quit thurbox and the agents keep running: Fleet runs them.

The engine

Fleet

Fleet runs coding-agent sessions. Each session is a Task: a file that names the agent, the place it runs, the repository and the brief. You apply it with fleet apply, and Fleet starts the session, keeps it running, delivers your messages and records the result.

Fleet works on its own. It is headless and needs no thurbox.

What Fleet is → Fleet features → 

fleet apply -f fix-login.json
fleet list task
fleet send fix-login "Run the tests too"

Get started with Fleet alone

curl -fsSL https://raw.githubusercontent.com/Thurbeen/thurbox/main/scripts/install.sh | sh -s -- --fleet-only
fleet init
fleet doctor
fleet up

--fleet-only installs fleet, runtime-mux and workspace-git, and nothing else. Install Fleet →
